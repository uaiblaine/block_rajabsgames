# block_rajabsgames audit, 2026-10-29

Scope: the fork at `master` (`779100e`, version 2026100300, release 1.2), installed on m503 (Moodle
5.3, mod_interactivevideo fork 2026102800). Four lenses: security, Moodle practice, performance (the
owner's priority), comments. Nothing in the plugin was changed.

Evidence levels: **measured** (probe or gate output on m503), **reproduced** (the failure was
triggered on m503), **read** (code reading, file:line given).

## How it was measured

`get_content()` was driven from a CLI probe inside `m503-webserver-1`: a generated course with
IV activities, 10 badges, 3 levels, a grouping of G groups, U enrolled students with one
`interactivevideo_completion` row per activity, and the block configured with the leaderboard,
the levels and the badges on. Reads are `$DB->perf_get_reads()` around one `get_content()` call for
a student; everything ran in one delegated transaction that was force-rolled back. The probe script
is not part of the repository.

| Group mode | G = 10 | G = 40 | G = 100 | Session hit |
|---|---|---|---|---|
| No groups | 17 reads | 17 | 17 | 0 reads, ~1 ms |
| Visible groups | 129 reads, 41 ms | 489 reads, 84-116 ms | 1,209 reads, 143 ms | 0 reads, ~1 ms |
| Separate groups | 25 reads | 85 reads | 205 reads | 0 reads, ~1 ms |

The count does not move with the number of students (50, 300 and 1,000 at G = 40 gave the same 489
reads); it is about 12 reads per group under visible groups and 2 per group under separate groups.
A cold render happens once per student, per block, per hour, and after every badge claim or refresh
click. The `$SESSION` payload is ~16 KB per student per block (G = 40).

## Security

**S1, high: cross-user read of completion details.** `ajax.php:42-50` takes `cmid` and `userid` from
the request and returns `interactivevideo_completion.completiondetails` for that pair. The only
guards are `require_sesskey()` and `require_login()` without a course (`ajax.php:28-29`): no course
or module login, no capability, no `userid == $USER->id`. Any logged-in user, including one enrolled
nowhere, can read every user's per-interaction details in every activity (the JSON carries answers,
XP, timestamps and report text written by other content types). `amd/src/main.js:68-79` is the only
caller and always sends the viewer's own id. Fix: drop the `userid` parameter and use `$USER->id`,
resolve the instance to its course module, then `require_login($course, false, $cm)` and
`require_capability('mod/interactivevideo:view', ...)`.

**S2, medium: any course's badge configuration.** `ajax.php:35-41` passes a client `courseid` to
`block_rajabsgames_get_configdata()` (`lib.php:117`) with no course login. It returns the badge list
(names, images, ids) and the block id of any course. For a course without the block it echoes a
warning-backed `null` that `main.js:98-100` then dereferences. Fix: `require_login($courseid)` and
return `{}` when there is no block. `classes/form.php` has the same shape: it reads the block of a
client-supplied `courseid` that is not tied to the IV activity the form edits (teachers only).

**S3, medium: badges are claimed by the client.** On a claim, `main.js:252-266` builds the new
`gameprogress` and the XP from DOM `data-xp` and posts them through IV's `save_progress`
(`main.js:357-380`). The IV fork re-derives the context and clamps the item's XP to its configured
maximum (`locallib.php:2019-2038`, `clamp_completion_detail`), so XP cannot exceed the item total.
But `gameprogress` is stored as sent: a student can claim every badge without reaching its timestamp,
and the block counts what is stored (`block_rajabsgames.php:192-219`). Fix in the IV contract: record
claims server-side from the badge id only, checked against the item's `content` and the viewer's
watched time.

**S4, medium: leaderboard population and privacy.** The leaderboard SQL
(`block_rajabsgames.php:404-423`) joins `{user}` to completion rows only: suspended, unenrolled and
deleted users stay on it as long as their completion rows survive. It shows first name, picture and
XP of the top five to every participant, with no capability to opt out and `$USER->firstname` /
`$top->firstname` instead of `fullname()` (`:290`, `:465`). The plugin ships no
`classes/privacy/provider.php` although `lang/en` already has `privacy:metadata`; a
`null_provider` fits (it keeps no rows of its own; the claims live in IV's table, which IV's provider
covers). Fix: join active enrolments (`get_enrolled_join` with `onlyactive`), use `fullname()`, add
the null provider and a `component_is_compliant()` test.

**S5, medium: editor-side stored XSS.** `main.js:724-774` builds `<option>` and `value="..."` markup
from `badge.name`, `badge.id`, `d.uniqueid` and `d.xp` by string concatenation. Badge names are
teacher input (`PARAM_TEXT` keeps `<`), so a teacher can run script in another editor's session on
the interactions page. `addinstance` carries `RISK_XSS`, which lowers but does not remove this. Fix:
build the nodes with `textContent` / `$('<option>').text()`.

Also read and found sound: `block_rajabsgames_pluginfile()` (block context, course login, single
file area, `send_stored_file`); the two dynamic forms require `block/rajabsgames:addinstance` in the
submitted context; all concatenated SQL values are integers from the database (no injection, but see
M1); both mustache triple-stashes carry `$OUTPUT->user_picture()` output only.

## Performance

**P1, high: `IN ()` kills the block.** Reproduced on m503:

- Separate groups, viewer in no group of the grouping: `implode(',', $mygroupids)` is empty
  (`block_rajabsgames.php:422`): `dml_read_exception ... syntax error at or near ")"`.
- Visible groups on a grouping with no groups: same error from the group leaderboard
  (`block_rajabsgames.php:351`).
- Read only: the edit form runs `annotationid IN ('')` when badges exist but the course has no
  usable IV activity (`edit_form.php:72-87`), so the teacher cannot open the settings to fix it.

A teacher who has no group, a newly created grouping, or a deleted last activity breaks the course
page block for everyone in that state. Fix: `get_in_or_equal()` with an empty-list short-circuit.

**P2, high: group membership in nested loops.** `groups_is_member()` costs two queries per call in
5.3 (`lib/grouplib.php`: `get_field` of the course, then `record_exists`). The block calls it once
per group for the viewer (`:330`) and, under visible groups, once per group for each of the top five
(`:471`): 2·G + 10·G reads. Measured: 129 / 489 / 1,209 reads for 10 / 40 / 100 groups. Fix: one
query of `{groups_members}` for the viewer plus the five leaders against the grouping's group ids
(`groups_get_user_groups()` is already cached for the viewer), and `get_group_picture_url()` only for
groups that are rendered.

Fixed on `MOODLE_503_STABLE`: the viewer's groups come from `groups_get_user_groups()` and the leaders'
from one `{groups_members}` query. The same probe now reads 15 under visible groups and 5 under separate
groups, at 10, 40 and 100 groups alike.

**P3, medium: the session cache trades freshness for one big recompute.** `:100-140` serves the whole
template context from `$SESSION` for an hour (0 reads, ~1 ms), then recomputes everything. XP, level
and rank therefore lag up to an hour behind the videos unless the student clicks refresh or claims a
badge (both call `block_rajabsgames_clear_session`). The payload (~16 KB, rendered picture HTML
included) rides in every request's session read. A MUC cache would serve this better: the
course-wide parts (totals, leaderboard, group ranking) in an application cache keyed by block and
invalidated by IV's completion events, the viewer's own XP from one indexed query
(`cmiduserid` index exists) on each render.

**P4, medium: video start latency.** `main.js:52-79` awaits `get_badges` and then
`get_completiondetails`, each a full ajax.php bootstrap, before any game UI, on every video load.
The progress is already in the annotations IV passed in. Fix: one call, or none (ship the badges with
IV's item payload and read progress from it).

**P5, medium: editor JS for every viewer.** `get_required_javascript()` (`:592-603`) loads
`block_main` for everyone who sees the block. That module statically imports
`core_form/modalform` and `core/templates` (`block_main.js:23-25`), and all its handlers except
`.rjg-refresh` are editor-only. Fix: load it only when `$this->page->user_is_editing()` and the
viewer can edit, with a tiny refresh handler for everyone, or import ModalForm lazily.

**P6, low-medium: handler hygiene in `main.js`.** The `timeupdate.games` handler (`:185`) runs
several jQuery selectors and a linear search per tick; it is `async` with no `await`. Un-namespaced
`.off('click', ...)` on `document` (`:217`, `:459`, `:470`, `:556`, `:567`) removes other IV content
types' handlers on the same ids. `:844` binds an input handler with no `.off`, so one more stacks per
server validation error; `:891` binds `timeupdate.rajabsgames` in the editor and never unbinds it.
`checkContentField` (`:714-783`) polls with `requestAnimationFrame` with no timeout.

## Moodle practice

**M1.** SQL by concatenation (`:148`, `:173`, `:195`, `:351-352`, `:406-423`, `edit_form.php:86`) where
the fleet requires `get_in_or_equal()`; parameters passed but never bound (`courseid`, `groupids`,
`mygroupids` at `:150`, `:430-436`, labelled "Get the group ids."). `LIMIT 5` inside SQL instead of
`$limitnum` (not portable to SQL Server). `SELECT completiondetails` as the first column of
`get_records_sql()` (`:192`): identical details from two activities collapse into one row, so a
badge earned twice counts once; the probe tripped core's duplicate-key debugging on it. Fix:
`get_fieldset_sql()` or select `id` first.

**M2.** The no-activity branch returns an array and leaves `$this->content` null (`:87-90`):
`block_base` then sees empty content and hides the block instead of the notice. Return
`$this->content = (object)[...]`.

**M3, fleet baseline.** Missing: `LICENSE`, `COPYING.txt`, `CHANGELOG.md`, `classes/privacy/`,
`tests/marketplace_readiness_test.php`, MAH `ci.yml` (the repo carries upstream's `gha.yml`, so
`mdl ci --matrix` cannot derive legs). `$plugin->supported = [400, 503]` and `requires = 2021112800`
while the declared dependency `mod_interactivevideo` needs 4.5: the floor should be 405, as for the
rest of the IV family. `version.php` dependency `ivplugin_richtext` is a subplugin of the mod
(fine). Hard-coded `xp` in `level.mustache:33`, `leaderboard.mustache:51`,
`groupleaderboard.mustache:44`; empty `Example context (json):` in every template; inline HTML
strings in `block_rajabsgames.php:63-66`, `:88-89` and `classes/form.php` (the fleet rule is zero
hand-built HTML in plugin code). styles.css: `!important` (34, 134, 138, 142), literal colours, IV
custom properties without `--bs-*` fallbacks (the block renders on course pages, where IV's tokens
may be absent). `db/services.php` declares `clear_session` as `type => read` although it writes the
session, and `execute()` never calls `validate_context()`. `db/install.php` appends to
`enablecontenttypes` and leaves a leading comma when the setting is empty. `edit_form.php:117`
JSON-encodes the whole block object (instance record and config) into the page. The cache definition
says `simpledata` but stores objects (`lib.php:144`).

## Comments

**C1, medium.** `main.js:32-41` documents `init` as "the decision plugin ... decision annotations"
(copied from local_ivdecision), and `runInteraction` (`main.js:905-991`) is local_ivdecision's code
whole: `#decision-q`, `getString('skip', 'local_ivdecision')` from a plugin this block does not
depend on, `this.start`/`this.end` read from a jQuery handler where `this` is the element. Delete
the method or make it a documented no-op, and rewrite the docblock.

**C2, low.** `ajax.php:18` and `db/uninstall.php` carry the scaffold's "describe file" placeholder; `amd/src/*.js`
and every template carry the same placeholder. `classes/main.php:19-33` has two class docblocks (2024 and 2025)
and `get_content()` is documented `@return string` but returns `true`. Both backup task classes
return `[]` beside the comment "We need to encode some attrs in configdata" (`backup...:48`,
`restore...:52`). `main.js:864` says duplicates are removed by uniqueid but only adjacent ones are;
`getPosition`'s default `'centercenter'` (`main.js:629`) matches no case. `block_main.js` `init` and
`main.js` `postEditCallback`/`renderEditItem` have no JSDoc. `@copyright` is the upstream author's,
which is right for a fork (no change suggested).

## The fork diverges as 5.3-only (owner, 2026-10-29)

The fork stops tracking upstream's version range. Done on branch `MOODLE_503_STABLE` (not committed):
`version.php` now declares `supported = [503, 503]`, `requires = 2026100500`, version `2026100500`
(the 5.3 namespace), release `1.2+uai.1`. `moodle-dev/plugins.conf` mounts it with `auto`, which
resolves to m503 and m503b; both stacks were upgraded to 2026100500.

What the decision changes in this report:

- M3's "floor should be 405" is settled by the divergence. The `ci.yml` to add has one job, for
  `MOODLE_503_STABLE`, with the full PHP × DB matrix.
- Compatibility code that can go: the five `self.isBS5 ? ... : ...` branches in `amd/src/main.js`
  (`:333`, `:727`, `:733`, `:753`, `:759`) become their BS5 side; `input-group-append` (`:742`, `:770`)
  is a BS4 class with no effect on 5.3; `external_compat::load()` in `classes/external/session.php`
  only aliases the external API for Moodle 4.0-4.1; `classpath` in `db/services.php` is redundant
  with autoloading.
- Tests may use PHPUnit attributes (`#[CoversClass]`, `#[DataProvider]`): no 4.5 leg runs moodle-cs
  any more.
- Upstream syncs become cherry-picks onto `MOODLE_503_STABLE`. Record the base upstream commit
  (`779100e` at the fork point) in the repository's `CLAUDE.md` when it is written, so later syncs
  can diff from it.

## Next: P3 and S3 needed a design decision

Both touch the contract with mod_interactivevideo, whose fork is ours too.

**P3, the session cache.** Done on 2026-10-29 with an event in the IV fork (owner's choice): see the
CHANGELOG. What follows is the note as written. Today each viewer's whole render (leaderboard included) lives in `$SESSION` for an
hour: 0 queries on a hit, but XP and ranks up to an hour stale, ~16 KB per viewer per block in every session
read, and a full recompute per viewer per hour (the browser check on 2026-10-29 met it: first names kept
showing after the fullname() change until the refresh button was clicked).

- Recommended: split the render. The viewer's own figures (XP, level, claims) are read on every render, two
  indexed queries (`cmiduserid` exists). The course-wide figures (leaderboard top five, group totals, badge
  counts) go to an application cache keyed by block, rebuilt on a miss and invalidated when a completion
  changes. The `$SESSION` copy and the refresh button go.
- What it needs from IV: a signal when a completion is written. IV fires no event on save today
  (`classes/event/` has interaction and deletion events, `xp_overridden`, nothing in `commit_item_completion()`).
  Either the IV fork adds a `progress_updated` event there (also useful to IV's own reports), or the block
  bounds staleness with a short TTL (for example 5 minutes) on the course-wide part.
- Decision for the owner: event in the IV fork, or TTL only.

**S3, client-asserted claims.** Done on 2026-10-30 as recommended, without the timestamp proof
(owner's choice): the type is server-graded and the player claims through `block_rajabsgames_claim_badge`;
see the CHANGELOG. What follows is the note as written. The player posts the whole `gameprogress` and the XP through IV's
`save_progress`; the fork clamps the XP to the item's total but stores the claim list as sent.

- Recommended: make the type server-graded, using IV's existing contract (`$servergraded`,
  `record_graded_completion()`, the `servergradeditem` refusal in `save_progress`). A new web service
  `block_rajabsgames_claim_badge(interactivevideoid, itemid, uniqueid)` checks that the position exists in the
  item's content and is not claimed yet, appends it under the item's lock and records XP as the sum of the
  claimed positions' XP. The player calls it instead of `save_progress`.
- Open question for the owner: whether a claim must also prove the viewer reached the position's timestamp.
  IV records no trusted watch position per user for this, so requiring it means new tracking (a server-side
  session start time is the cheapest bound). Without it the fix still stops invented badges, duplicate claims
  and XP that does not match the claims, but a learner can still claim a real badge without watching.
